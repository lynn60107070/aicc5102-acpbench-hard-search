Can an LLM plan
better by searching?

Reproducing ACPBench-Hard and testing LLM-guided search on its Next Action task

Presented by Lynn Younes · Faheema Hassan Kudukky · Aisha Suleiman Shaik Date 24 November 2026
Introduce the team and the question in one line: we reproduced a planning benchmark for language models, then tested whether letting the model search through its options helps it plan.

Does best-first search over LLM-predicted states beat answering once?

01.

The paper scored one answer per question. It never tested more compute at answer time.

02.

Search helped LLMs on puzzles and maths (Tree of Thoughts, RAP). Planning is the obvious next test.

03.

We tested it fairly: same questions, matched budget, 3 seeds, fixed in our proposal.

The brief asks for one experiment the paper did not do but should have. The paper only measures single-shot answers; inference-time search is the natural question it leaves open. The research question was fixed in the proposal on 29 September.

The task

choose the next move

ACPBench-Hard (Kokel et al., ICLR 2026) tests planning skills one at a time, open-ended: the model must write its answer.

Next Action: given a state and a goal, name one action that brings us one step closer on an optimal plan.

130 test questions from 13 domains. A validator with a planner checks every answer.

Example · ferry domain

The ferry is at l1 and empty. Cars c0 and c1 are at l0. Goal: c0 at l1.

What is the next action that takes us towards the goal?

(sail l1 l0)

Correct if it can be applied now and the shortest remaining plan gets one step shorter.

Llama 3.1 8B gets only 25 percent on Next Action in the paper. Unlike PlanBench, which grades whole plans pass or fail, ACPBench-Hard asks about one moment, so it shows which skill breaks. The example is simplified from a real ferry question.

The rule

The LLM does everything: no planner, simulator or validator during search. Budget: 14 calls per question.

One expansion costs 1 + 2k = 7 calls with k = 3, so 14 calls allow the root plus one child. The validator only grades the final answer. The proposer samples at temperature 0.7; predictor and evaluator are greedy. Search worked for Tree of Thoughts and RAP, so it was a reasonable bet for planning.

This animates one search on one question; the scores shown are illustrative. Propose: one call lists three actions. Predict: three calls write the state after each; one says NOT APPLICABLE and is pruned, so it is never scored. Score: the evaluator rates each surviving state 0 to 10. Expand: we repeat from the best state, which costs up to seven more calls. Answer: we return the first move on the path to the highest-scored state. Pruned candidates (never scored) and a few unparsable proposals are why search averages 13.4 calls rather than 14. The validator never sees any of this; it only grades the final answer. Press R to replay.

Matching tokens instead of calls does not change the conclusion: best-of-N is higher than search in all three seeds (p = 0.557, 0.281, 0.036).

Key finding

The model can propose the right move,
but cannot recognise it.

31%

a correct action is among the 3 proposed (8B; 59% for 70B)

0.58

AUC of its own scores, correct vs. wrong (0.5 = chance; 70B: 0.53)

16%

final accuracy: most found answers are lost at selection

This is the main finding. Coverage is an analysis metric only, computed after the run with the validator, never seen by the search. A bigger model proposes much better candidates but judges them only slightly better. Judging a move needs the same planning skill the model lacks: evaluation, not generation, is the bottleneck.

Limitations

01.

One task, two model sizes, 130 questions: wide intervals.

02.

Closed-model rows cannot be rerun: retired APIs.

03.

Numbers vary with serving precision, so we pinned one provider.

04.

Small budget: 14 calls per question; about $27 in total.

05.

The follow-up came after the main results: post-hoc.

One answer moves accuracy by 0.008. Saying the limitations before being asked is part of reporting honestly. Very large models (405B) and reasoning models were beyond the budget.

Takeaways

by facts

The paper reproduces

8B and 70B, both tasks, inside the interval.

→

Search without a verifier does not help

The model barely tells its good candidates from bad ones.

→

Scale helps generation far more than judging

70B proposes much better, scores only slightly better.

Next step: a reliable evaluator

Learned or symbolic, like LLM+P.

Search prompts

Proposer · temp 0.7 · ≤ 200 tokens
List <k> different actions that can be applied in the current state and that could move us towards the goal, most promising first. Write each action on its own line, in parentheses … Write only the actions.
Predictor · greedy · ≤ 600 tokens
Consider applying the action <action>. First check whether it can be applied in the current state. If it cannot, reply only: NOT APPLICABLE. Otherwise describe the complete resulting state …
Evaluator, frozen · greedy · ≤ 400 tokens
How close is this state to the goal, on a scale from 0 (no progress) to 10 (goal reached)? Reason briefly in at most three sentences, then end with a final line of the form: Score: N
Direct · official prompt, 2 examples
**Question**: <problem> What is the next action that takes us towards the goal? … Provide only the action. **Final Answer**:

Non-root nodes add: "Ignore the current state given in the description above. After applying <path>, the current state is: <predicted state>". Full text in Appendix B.
