Can an LLM plan
better by searching?

Reproducing ACPBench-Hard and testing LLM-guided search on its Next Action task

Presented by Lynn Younes · Faheema Hassan Kudukky · Aisha Suleiman Shaik 24 November 2026
Introduce the team and the question in one line: we reproduced a planning benchmark for language models, then tested whether letting the model search through its options helps it plan.

Does best-first search over LLM-predicted states beat answering once?

What the paper measured

One answer per question. The same model never got more calls at answer time.

What we test

Let the model search: propose, predict, score, expand. Same model, same 14-call budget as best-of-N, no simulator.

Search with the LLM as its own world model helped on puzzles, maths and Blocksworld (Tree of Thoughts, RAP); open-ended planning across 13 domains, at a budget matched to best-of-N, is the open test. Fair test: same questions, matched budget, 3 seeds, fixed in our proposal.

The brief asks for one experiment the paper did not do but should have. The paper only measures single-shot answers; inference-time search is the natural question it leaves open. The research question was fixed in the proposal on 29 September.

The task

choose the next move

ACPBench-Hard (Kokel et al., ICLR 2026) tests planning skills one at a time, open-ended: the model must write its answer.

Next Action: given a state and a goal, name one action that brings us one step closer on an optimal plan.

130 test questions from 13 domains. A validator with a planner checks every answer.

Example · ferry domain

The ferry is at l1 and empty. Cars c0 and c1 are at l0. Goal: c0 at l1.

What is the next action that takes us towards the goal?

(sail l1 l0)

Correct if it can be applied now and the shortest remaining plan gets one step shorter.

Llama 3.1 8B gets only 25 percent on Next Action in the paper. Unlike PlanBench, which grades whole plans pass or fail, ACPBench-Hard asks about one moment, so it shows which skill breaks. The example is simplified from a real ferry question.

The rule

The LLM does everything: no planner, simulator or validator during search. Budget: 14 calls per question.

One expansion costs 1 + 2k = 7 calls with k = 3, so 14 calls allow the root plus one child, and calls saved by pruning can start a third expansion, of the next root child. The validator only grades the final answer. The proposer samples at temperature 0.7; predictor and evaluator are greedy. Search worked for Tree of Thoughts and RAP, so it was a reasonable bet for planning.

This animates one search on one question; the scores shown are illustrative. Propose: one call lists three actions. Predict: three calls write the state after each; one says NOT APPLICABLE and is pruned, so it is never scored. Score: the evaluator rates each surviving state 0 to 10. Expand: we repeat from the best state, which costs up to seven more calls. Answer: we return the first move on the path to the highest-scored state. In the real search the call saved by pruning goes to proposing from S₂, the next root child; the budget then runs out, so the answer stays a₁. Search averages 13.4 calls rather than 14 mainly because 3% of proposals parse to no action, and partly because of pruning. The validator never sees any of this; it only grades the final answer. Use the arrow keys or the ‹ › buttons to go one step at a time; R goes back to step 1.

This is the main finding. Coverage is an analysis metric only, computed after the run with the validator, never seen by the search. The AUC compares a correct and a wrong candidate of the same question, which is what the search has to do; 8B is at chance. A bigger model proposes much better candidates and selects better too: its search beats its own first proposal, 0.36 against 0.28. It removes 71% of impossible moves, against 14% for 8B, but also 23% of possible ones. And it picks the correct candidate in 61% of the questions where it proposed one, against 43% for a random pick. But most of that is pruning: after pruning, a random pick already gets 56%, and the proposer's first remaining candidate 60%, so the 0 to 10 scores add almost nothing. Its AUC of 0.58 has a wide interval, 0.47 to 0.68, so we don't lean on it. Judging a move needs the same planning skill the model lacks: evaluation, more than generation, is the bottleneck.

0.331 ± 0.027 · self-consistency on the structured prompt · above direct in every seed (p = 0.043, 0.005, 0.058) · above best-of-N at the same 14 calls (seeds pooled p = 0.003, Holm 0.02) · 18× direct’s tokens.

Both follow-ups came after the main results, suggested as a bonus at the progress check. Each was tried on the 40 validation questions with a pass bar fixed in its code before running. Then we pre-registered a repeat on 70B before running it: 0.492, against best-of-N 0.364 at the same 14 calls, significant in every seed and after Holm correction, and above the paper's 70B value of 0.42, though not significantly against that number. At 70B most of the gain is the structured prompt itself, 0.469 with one call. Fair framing: the paper's 0.25 is one call; ours uses 14 calls and about 18 times the tokens, so the fair win is against best-of-N at the same 14 calls, plus 0.10, pooled p = 0.003. It is self-consistency, Wang et al. 2023, applied to the structured prompt. Under the 14,000-token cap it reaches 0.321 vs 0.210, but its calls are long and it overshoots the cap on almost every question (15,036 tokens on average), so quote the per-question token-matched figure: 0.313 against 0.210. Against the paper's 0.25 alone, only seed 2 is significantly higher. Its gain over a single structured call is small: at 8B it is significant only in seed 2 (pooled p = 0.03, not after Holm correction), and at 70B voting adds only +0.023 (p = 0.50). So much of the gain is the structured prompt itself; neither asks the model to judge its own candidates, which fits the main finding.

What did we take from each?
From RAP: the LLM as a world model that predicts the next state. From Tree of Thoughts: the LLM judging its options (our “vote” ablation is ToT’s evaluator). So our search is closest to RAP.
Why did search help them but not us?
Their searches had good judges: designed rewards, or puzzles that are easy to check. Ours relies on the LLM judging itself, and on open-ended planning it judges near chance. Search only works if the judging works.
Paper Section 2. One line: our search is closest to RAP, but best-first, every judgment including applicability comes from the LLM with no task-specific rewards, 13 domains, and a matched budget.

The key comparison
Search and the bonus both add more calls and more reasoning. The only difference is whether the LLM judges its own options, and that takes 8B from worst (0.159) to best (0.331).
Did the controls help on their own?

It is the control for step-by-step reasoning. Proposing three and choosing would be judging, i.e. search in one call. The 14-call version of structured is the bonus.

How the model picks what to write
At each step it has a probability list (illustrative):

With greedy, all 14 answers would be identical, so the vote needs sampling.

Validation set vs test set?
Both come from the paper’s dataset. Validation: 40 questions from 8 of the 13 domains, used only to try out and choose the design. Test: 130 questions, 10 per domain, run only after the freeze. They never overlap.
What was chosen on validation?
The evaluator (0–10 score), candidates k = 3, depth d = 2, budget 14 calls, pruning of NOT APPLICABLE moves, the three prompts, and the temperatures. Frozen on 23 Oct, before any test run.

Before the freeze, an early prototype ran on 10 test questions just to check the code worked. Nothing was tuned on it, and the paper reports it (Section 4).

Likely questions: results and the bonus

Does search fail on 70B?
Not significantly different from direct: 0.362 vs 0.377, interval −0.09 to +0.06. Say “not significantly different”, never “no effect”.
Isn’t generation the bigger problem?
Generation sets the ceiling. For search, extra candidates raise “correct move found” from 22% to 31% on 8B, and selection drops it to 16%. So “more than generation”, not “only”.
What if every candidate is pruned?
The search returns the proposer’s first candidate. On 70B: 70 of 390 searches (7 correct, 57 inapplicable). No re-proposal step: a known limitation.
Did you beat the paper?
Only as numbers: 0.331 vs 0.25 and 0.492 vs 0.42 (the 70B one not significant). The paper uses 1 call, we use 14, so the fair comparison is best-of-N at 14 calls: 0.231 and 0.364.
Isn’t the bonus post-hoc?
On 8B, yes, and we say so. That is why the 70B repeat was pre-registered: committed on 22 Nov before any run, reported whatever came out.
Is the bonus just the structured prompt?
On 70B mostly: one greedy structured call scores 0.469 (vs direct p = 0.0501, not significant); voting adds +0.023.

It shows repeated sampling with a majority vote can match complex methods at lower cost, so methods must be compared at equal cost. That is why our main control is best-of-N at the same 14 calls.

Skills, tasks vs domains, and what a planner is

What does “splitting planning into skills” mean?
Like a driving test that checks rules, signs and turns separately instead of only “did you reach the airport?”. A plan needs several abilities: which moves are possible now, what a move changes, whether a plan works, which move to take next. Testing each one separately shows which ability breaks.
PlanBench vs ACPBench vs ACPBench-Hard?
  • PlanBench: generate a whole plan, graded pass or fail.
  • ACPBench (2025): 7 separate skills, asked as yes/no or multiple choice: the model picks.
  • ACPBench-Hard (ours): the same 7 skills plus Next Action, open-ended: the model must write the answer.
Are the skills the tasks or the domains?
The skills are the tasks: what is asked (Applicability, Progression, Next Action…). The domains are where it happens: the 13 puzzle worlds (ferry, Blocksworld, logistics…). Every task is asked in every domain: 8 × 13 × 10 = 1,040 questions. We used the Next Action row: 13 × 10 = 130.
What is a planner?
A classical, deterministic program, not an AI. Given the start state, the goal and the action rules in PDDL, it systematically searches move sequences, like a GPS checking routes, and finds a plan, often the shortest. Always correct, but it needs the problem in PDDL and can be slow on large problems. It is inside the validator and LLM+P, never in our search.
Ferry example of the skills: applicability "can c0 board now?"; progression "after sailing, where is the ferry?"; validation "does board, sail, debark work?"; Next Action "what should we do next?". In LLM+P the LLM only translates English into PDDL; the planner does the planning.

Where the model’s choices come from

1Training
Trained on huge amounts of text with one job: guess the next word, billions of times. It learns patterns: which words tend to follow which.
2Answering
It reads our question (domain, state, goal, two examples) and scores every possible next word by how well it fits those patterns.
3Probabilities
Scores become percentages that add up to 100%. Temperature sets how spread out they are:
T = 0 (greedy)
T = 0.7 (ours)
high: near random
The model does not know the answer; it estimates
  • “sail 60%” is a confident guess, not knowledge: board at 30% might be the correct move.
  • Sampling rolls a weighted dice per word, so repeated calls differ; one different early word changes everything after it.
  • The vote then returns the answer given most often. The spread shows confidence: 13 of 14 agreeing vs a 5 / 5 / 4 split.
  • Plain best-of-N barely beats one greedy answer (0.231 vs 0.223): the vote mostly lands on the top guess. Voting helps more on structured reasoning (0.331).
Patterns, not the puzzle’s rules
The probabilities say what usually follows text like this; the model never checks whether a move is possible. That is why:
  • its most common error is an impossible move (75.7 per run of 130 on 8B);
  • its confidence is a poor judge of its own candidates (within-question AUC 0.48 on 8B).
The validator is the opposite: it applies the formal rules with a planner, so it checks instead of guessing.
Numbers in the probability example are illustrative. Technically the model scores tokens (pieces of words), and a softmax turns the scores into probabilities; temperature divides the scores before the softmax.

Holm correction: which wins still count

Why correct at all
p < 0.05 allows a 5% chance of luck per test. Run 20 tests where nothing is real and about one still looks significant. We ran 12 seed-pooled tests, so the bar has to rise.
How Holm works
  • Sort the p-values, smallest first.
  • Multiply each by the number of tests still in play: 12, then 11, then 10…
  • Stop at the first one above 0.05; it and all after it do not count.
McNemar vs Holm
McNemar is a test: is A better than B on these questions? Holm is a correction applied afterwards to many tests’ p-values. First test, then correct.
